THE SHARED ROOT CAUSE - CONFIRMED
  Your hypothesis was right. #1's three symptoms, #3, and #4 are all the
  same defect class: THE WRITE LANDS CORRECTLY, THE READ LOOKS ELSEWHERE.
    - QUAD 'OK' confirm  -> bot_state.quad_last_confirmed_at
      header read        -> max(quad_regime_history.effective_at)
      History only gets a row on a VALUE CHANGE, so 'last confirm' really
      meant 'last change' (8/02). Your 8/17 OK was stored and ignored.
    - hdg ranges         -> hedgeye_risk_ranges.buy_trade/sell_trade (daily,
                            upsert works, data verified present)
      report bands read  -> mfr_snapshots only. The hierarchy was never
      implemented on the read path: v_screener's hedgeye CTE selected the
      trend WORD only. 'hdg' labels on rows were the trend source, never
      the band source.
    - OutBucket trends   -> hedgeye_signal_changes (parsed correctly since
                            forever: XLU out_bucket BEARISH 7/31 was there)
      trend gate read    -> latest hedgeye_risk_ranges row, no age bound.
      XLU froze at 7/30 BULLISH and beat the correct value in COALESCE.
      A purpose-built staleness gate exists in db_pg (RR_MAX_AGE_DAYS) -
      this path simply never called it.
    - vol divergence     -> same table, two anchors. Stat pack anchors on
      last_completed_session (ET, correct). Report anchored on
      date.today() = UTC wall clock, AND the nightly writer stamped rows
      with the UTC date at 00:02 UTC = 20:02 ET, so the '8/21' row was
      built from THURSDAY-EVENING data. The report's VIX 16.0 [11.7-15.9]
      rp=1.03 was a phantom: Thursday band + overnight futures-flip price.
      THE PACK WAS THE CORRECT ONE. Not a live-vs-close design choice.
